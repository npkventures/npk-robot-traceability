# Product entry and access correction

This correction implements the November 18 direction in [build.md](../build.md). It is a product integration and security correction, not production launch acceptance.

## Diagnosis and delivered behavior

The default development command opened the static/local preview. Its Workspace link opened a file-only editor, while the actual Supabase-backed product was in `beta/`. The server demo reused that editor without a restricted demo mode, so it accepted user imports. Account entry, organization administration, history, projects, machines and integrations already existed, but entry points were secondary and session failure could leave old records visible.

`npm run dev` now starts the combined product on port 3002. `npm run dev:preview` explicitly starts the standalone preview. Public navigation exposes sign-in, get-started, open-product and demo. `/login?mode=signup` opens registration; `/app?org=<UUID>` retains a validated team destination through login and same-tab provider returns. Only actual memberships are selectable. A sole membership opens automatically; multiple memberships require a choice unless a permitted team was requested. A missing membership presents invitation and founder-assisted onboarding paths, without granting access. Invitations require explicit acceptance and server-verified ownership. Pending invitation tokens and validated destination references are stored only in that tab's session storage, cleared on acceptance/sign-out; no record bundles or session credentials are stored there. Separate-tab email confirmation may require reopening the invitation.

The standalone static export cannot authenticate. Its account page explains that distinction rather than silently displaying a demo as a customer workspace. Deploy the combined `beta/` server for the actual product; deploying `out/` alone does not deliver customer access.

## Demo isolation

Both public demo routes use `app/demo/shared-demo.tsx` and `app/local/workspace.tsx` with a fixed, cloned synthetic fixture. Demo mode discards any supplied hosted adapter. It exposes comparison, evidence, history and investigation reading, with no file import, record mutation, team management, collector transport, integration callback, save callback, or analytics callback. It does not read browser record storage. Evidence references remain text and are never fetched. Reload starts from the fixture. The real workspace uses a separately instantiated authenticated adapter and receives only API-authorized organization records.

The URL is not the security boundary. Component capability separation prevents normal demo interactions from invoking private adapters; independent authentication, current memberships, role checks, row-level security, scoped credentials and database relationship checks protect the APIs even if someone manually constructs a request from the demo page. A signed-in person can intentionally navigate to the product; cookies are not treated as an entitlement to arbitrary tenants. This assumes trusted application JavaScript, as does the real workspace; deployment security and XSS defenses remain necessary. No sandbox iframe or separate data store is needed for a fixture-only reader with no remote operations.

## Authorization and session handling

`lib/beta/server.ts` verifies the provider user and approved session, reads membership through the user's database token, and dispatches privileged mutations only to role/scope-checking database functions. The stale-tab account header is an additional rejection check; it never grants access or selects the acting identity. Member roles, project grants and billing claims supplied in a request body cannot replace server authority. Streams recheck access. Tenant-qualified foreign keys prevent cross-organization references. Anonymous clients cannot call privileged RPCs or read private tables. No raw file-storage service is implemented: imports are approved metadata, exports are authorized responses, and evidence files are external references rather than publicly served uploads.

The client invalidates outstanding requests when account/team context changes, removes records on authorization/session loss, verifies access on focus and periodically, hides protected content during that check, handles restored browser history, and broadcasts account changes to other tabs without retaining private data. Password changes bind to the displayed account. An inactive tab rechecks on return; the server authorizes every request regardless of the polling interval. Unsaved drafts are discarded on lost access, so revoked users cannot retain an editable stale interface. Network failure during access verification closes the loaded workspace and offers reload/sign-in recovery.

Robot records are the default workspace view; History and team tools exposes the existing administration and history panels. Pending invitations and accounts without a team retain visible onboarding controls. Owners/admins retain existing team tools; engineers/members retain record editing. Viewers/internal viewers read and export. Operators can append a run against an existing first-revision setup through the shared Record form; the adapter sends only new runs and exact dependencies, and existing SQL restrictions still apply. Corrected configurations and new configuration preparation require an engineer. Team/project, machine, lifecycle, report and integration panels remain governed by their existing feature flags and permissions.

## Missing commercial and external pieces

No billing SDK, checkout, subscription table, entitlement state, paid activation service or commercial enforcement policy exists in this repository. A pilot review's “continue paid” value is a proposal only. Access remains invitation-led; registration and booking grant neither membership nor paid access. Introducing subscriptions requires a commercial policy and provider configuration; this task does not invent either or claim an available paid checkout.

Supabase remains the working auth system. The approved [Clerk migration](clerk-migration.md) has not been activated and still needs its recorded prerequisites. Actual Google/GitHub OAuth acceptance, email inbox delivery, final HTTPS deployment/redirect configuration, managed recovery acceptance and customer workflow validation are not established by this correction. Integration mocks and simulated commands are not live CAD or physical-robot execution. See [build progress](build-progress.md) for the exact tests performed and current limitations.
